# LSU 仲裁退步診斷與下一版建議

2026-11-16（Asia/Taipei）。唯讀重播 A+B 與仲裁 v1 的 PID、FFT、statemate；
**沒有修改 CPU RTL，也沒有更新全工作負載分數或實體資格。**

結論：首次 head store 讓 load 先走，每次都多付兩拍 store 退休等待。
PID 的後續浮點相依鏈能受益；FFT／statemate 的大部分讓行發生在 ROB 15／16 格，
其中一些讀取最後被分支復原取消。建議先試 ROB 空間條件，再決定是否保留這條仲裁路線。

## 量測可信度與範圍

- 原 A+B、仲裁 v1 的生成模型／runtime objects 與已公開 archive 完全相同；
  僅以固定 GCC 11.4 重連接唯讀 host observer。
- 三工作負載、兩版本，共六組 observer 開／關對照（12 次執行），stdout、memory audit、
  完整 profile 均重現原始量測。ELF、CPU 10,000 ps、三種記憶體 10,000 ps 不變。
- A+B PID 全 8,256 拍的 39 個訊號與先前獨立 VCD 擷取相符。
  六份原始串流共 **5,504,081 拍**，互斥週期、逐 PC 退休／等待與事件分母逐一核對。
- 兩版本各工作負載的**完整退休 PC／指令順序**雜湊相同；不只比較各 PC 次數。
  外部 load 逐 ROB tag 追蹤到退休或退休時分支 flush；沒有 ROI 結尾未決讀取。
- 實際資料的錯誤 commit PC、截斷 row 兩個負向控制均被拒絕。

[工具與重現方式](../experiments/lsu-arbitration-diagnosis-v1/README.md)、
[完整原始證據](evidence/2026-11-16/lsu-arbitration-diagnosis/README.md)。

## 已確認的代價與收益

| 工作負載 | 總週期 A+B → 仲裁 v1 | 讓行次數 | 讓行 load 最後退休／取消 | 讓行 store 多等的拍數 |
| --- | ---: | ---: | ---: | ---: |
| PID | 8,256 → 7,238 | 511 | 510／1 | +1,022 |
| FFT | 33,656 → 34,851 | 1,214 | 886／328 | +2,428 |
| statemate | 2,614,289 → 2,805,791 | 129,628 | 83,470／46,158 | +259,256 |

按完整退休順序配對 **499,588 筆 store**：所有被讓行的 store 在 A+B 的
mark→retire 均為 1 拍，仲裁 v1 均為 3 拍。沒有推測這些 store 在兩版本是同一個
tag；分支復原會改變後續 tag，配對依據是已驗證相同的程式退休順序與 PC。

FFT 其他 store 再多等 207 拍，store-ack 總差為 +2,635。
statemate 其他 store 合計少等 3,928 拍，總差為 +255,328。
這些數字與既有互斥 profile 完全相符；其餘 load／運算等待減少才形成最終總週期差，
不能把 store 等待直接當成可全部省下的時間。

PID 第 2 筆 ROI store 的實際時序：

| 事件 | A+B ROI cycle | 仲裁 v1 ROI cycle |
| --- | ---: | ---: |
| 下一迴圈 load `800001e8` 接受 | 78 | 76 |
| store `80000204` 接受 | 76 | 78 |
| 該 store 退休 | 77 | 79 |
| 相依 FMA `800001f4` 發射 | 81 | 79 |

仲裁改變了 load／store 順序，這個例子的 FMA 提早兩拍。全 ROI 的最終淨改善
仍以實測 **−1,018 cycles** 為準，不把單一例子外推為每個迴圈完全相同。

## 多出的讀取去哪裡

| 工作負載 | 外部讀取 A+B → v1 | 最後退休的外部讀取 | 被分支復原取消 A+B → v1 |
| --- | ---: | ---: | ---: |
| PID | 519 → 520 | 518 → 518 | 1 → 2 |
| FFT | 6,026 → 6,382 | 5,407 → 5,407 | 619 → 975 |
| statemate | 349,607 → 390,854 | 316,217 → 316,217 | 33,390 → 74,637 |

FFT 增加的 **356** 次、statemate 增加的 **41,247** 次外部讀取，數量差額全部落在
被取消的類別。這是完整生命週期核對，並非從總讀取量猜測。FFT 另有 512 筆、statemate
另有 1 筆退休 load 沒有 ROI 內外部請求，兩版本數量相同；可能為轉送或跨 ROI 邊界。

例：FFT 的第 65 筆 store `80001274` 於 cycle 390 讓 `800012ac` 的 load 先走，
ROB 為 15 格；392 拍已滿 16 格且 rename 受阻，store 到 393 才退休。
這個 load 在 403 拍的退休時分支復原被取消。
statemate 第 124 筆 store `80001dc4` 也在 15 格時讓行；load `80001914`
於 746 拍接受、748 拍完成，最後在 758 拍被取消；store 由 mark 起多等兩拍。

這些例子與全體計數支持「有限頻寬用在較遠、可能被取消的 load，同時延後 head store」
這個問題。分支 flush 數量也隨排程改變，不能宣稱只消掉這些讀取就必然回收全部退步。

## 建議下一個獨立實驗

**先試 ROB 空間限制：僅剩一格或已滿時，首次 head store 維持優先；至少兩格可用才允許讓行。**
它針對退休受阻時 ROB 即將填滿的情況，保留原有首次一次的上限。
已經在回壓中送出的 load 必須繼續保持，不能因空間門檻變動撤回或切換請求。

以下是將條件套在這次已錄下的 v1 軌跡，**只是涵蓋率，不是新 RTL 結果或效能預測**：

| 條件 | PID 保留讓行 | FFT 保留讓行 | statemate 保留讓行 |
| --- | ---: | ---: | ---: |
| v1 原策略 | 511（取消 1） | 1,214（取消 328） | 129,628（取消 46,158） |
| ROB 至少兩格可用 | 511（取消 1） | 119（取消 0） | 17,678（取消 2） |
| 備選：load 與 head store 序號距離 ≤4 | 511（取消 1） | 68（取消 0） | 11,784（取消 0） |

ROB 條件會排除既有 FFT 讓行的 **90.20%**、statemate 的 **86.36%**，並保留 PID
全部 511 次。它需要將 ROB 空間狀態送到 LSU，多一條控制路徑；目前最緊路徑已在
INT EX0→dmem 位址，必須重新量測時序，不能沿用父版 slack。

序號距離備選可使用 LSU 已有 tag，介面代價較小，但「4」目前只是從這份軌跡提出的
候選門檻，不能視為普遍最佳值；不建議同時疊加兩個條件，否則不易判定改善來源。
也不建議依 PC／benchmark 名稱特判，或直接只允許 FP load：FFT 本身也有被取消的 FP load。

下一步由使用者共同選擇條件後，建立獨立候選、測試門檻變動／回壓／flush／fault、
完整 27 項和數值／退休工作量，再比較兩類分數及個別退步。值得保留才進行新的
ASAP7 TT／SS／FF global-route 資格。兩類 ≥1.20×、面積 ≤1.10× 目標保持不變。

目前 [critical paths](CRITICAL_PATHS.md)仍是已完成實體資格的 A+B 父版：
SS 9.4 ns 的 INT EX0→dmem address 最小 setup **+8.20 ps**，FPU→completion
**+59.46 ps**；FF hold 最小 **+17.58 ps**。新仲裁的實體結果尚未產生。
