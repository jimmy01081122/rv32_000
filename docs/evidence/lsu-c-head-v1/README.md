# C 隊首 load 提前退休的共同時脈結果

C 在 ROOM 仲裁上只改一件事。當 LSU 已緩存成功的外部讀取回應、完整 ROB 標籤與未完成隊首 load 一致時，結果可於同一個時脈邊緣寫入實體暫存器並退休。傳送給整數或 FP 目的暫存器的資料與提交紀錄共用相同的取值及延伸邏輯。

CPU 模擬週期與記憶體服務時間各固定為 10 ns。兩個工作負載家族都用原始 ELF。FP32 的 DSP 四項與矩陣／ML 四項各佔一半權重。RTL、建置與量測來自乾淨提交 `47c18f98093e`。

| 家族 | ROOM／原始基線 | C／原始基線 | C／ROOM |
| --- | ---: | ---: | ---: |
| Embench 19 項 | 1.076286× | 1.079442× | 1.002933× |
| FP32 八項 | 1.109010× | 1.111306× | 1.002071× |
| FP32 DSP | 1.108623× | 1.113207× | 1.004135× |
| FP32 矩陣／ML | 1.109396× | 1.109408× | 1.000011× |

對 ROOM 的 27 組配對中，24 項週期減少、3 項持平、0 項增加。C 的兩個家族都仍低於 1.20×。C 的標準元件面積、可用時脈與 global-route critical path 待量測。最近取得三角實體結果的候選為 ROOM。[逐項週期與工作量](review.json) · [ROOM 實體報告](../../LSU_ROB_ROOM_PHYSICAL.md)

先前關注的 `statemate` 從 ROOM 的 2,628,051 拍降至 2,610,364 拍，也低於 A+B 的 2,614,289 拍。[A+B 的同頻成績](../2026-11-13/lsu-ab-complete/complete-review.json)

## 減少的等待去了哪裡

在完整 27 項 ROI 中，隊首 load 等待自己已緩存外部回應的歸類從 3,464,879 拍變成 0 拍。各工作負載的退休指令類別、逐 PC 指令與次數皆與 ROOM 及原始基線一致。

GEMM 維持 123,372 拍。隊首等待 FP load 減少 8,240 拍，等待 FP store 增加 7,500 拍，等待乘法增加 740 拍。Cholesky 的隊首 FP load 等待減少 10,591 拍，FMA 等待增加 9,850 拍，除法增加 705 拍，總共只省 3 拍。這些值來自互斥的隊首週期分類，記錄同一拍由哪一種指令佔據隊首。

將每項工作負載的週期占比等權平均，等待 store 退休確認（`store_ack_wait`）占 Embench 的 5.95%、FP32 的 9.71%。其中隊首 store 尚未標記（`mark_pending`）分別占總週期的 4.36% 與 6.26%。此分類也包含當拍已送出請求的情形。建議下一個診斷對齊 store 位址與資料就緒、請求握手及成功或錯誤回應的時脈邊緣，以量出實際可省的等待。[完整逐項資料](inventory.json)
