# C 的 store 退休逐拍診斷

在固定 100 MHz CPU 與 10 ns 記憶體下，27 項工作負載的 ROI 共退休 **3,251,340 筆 store**。每筆外部寫入都在請求被接受後一拍收到成功回應，並在回應的同一個邊緣退休。要減少可見的 store 等待，優先機會在請求送出之前。

| 事件或互斥週期分類 | Embench 19 | FP32 8 |
| --- | ---: | ---: |
| 等待 store 退休確認（合計） | 5.952% | 9.711% |
| 寫入請求握手 | 4.358% | 6.260% |
| 當拍讓行給新 load | 0.609% | 1.191% |
| 等待在途 load 回應握手 | 0.985% | 2.260% |
| 其中首次取得 store 授權時即遇到 load 回應 | 0.376% | 1.069% |
| 取得授權之前的隊首 store 等待（另一組週期） | 0.697% | 1.029% |
| 其中 AGU 正在寫入 SQ 且資料埠可用 | 0.585% | 0.958% |
| 其中只缺 store 資料運算元 | 0.000% | 0.000% |
| 其中只缺位址基底運算元 | 0.000% | 0.000% |
| 其中兩個運算元都還沒就緒 | 0.000% | 0.000% |

每項先除以自身 ROI 週期，再於家族內等權平均。前四列中，寫入握手、讓行新 load 及在途 load 回應三者加總為等待確認的全部週期。已有在途 load 的列是回應列的子集。授權前的等待屬於 ROB 隊首 store 尚未完成的階段，與確認等待分開計算。[機器可讀的逐項計數](review.json)

授權前的分類只在 store 仍位於 issue queue 時判讀個別運算元。其餘週期中，Embench 有 73,941 拍、FP32 有 168 拍是隊首 store 兩個運算元已就緒但仍在 issue queue。另有 5,573 個 Embench 週期觀察不到對應的 issue queue 項目，當拍也沒有首次 AGU 寫入，保留為獨立分類。

## 仲裁與資料就緒

- Embench 的 3,223,774 筆 store 中，2,534,639 筆（78.6%）在首次授權當拍就取得資料埠。FP32 是 21,546／27,566 筆（78.2%）。舊 profiler 的 `mark_pending` 包含這些已經握手的週期。
- 27 項共有 458,316 次 store 就緒但首次讓行給新 load。這筆讀取佔用了一個請求邊緣，下一拍回應時單一在途交易的外部埠尚不能接受新寫入。改變優先序也會改變該 load 與相依指令的進度，因此這兩拍不能直接換算成程式加速。
- SQ 的有效位址與格式化後的資料由 AGU 同拍寫入。整數 issue queue 分別記錄位址基底與 store 資料的就緒位元。以 GEMM 為例，8,000／8,000 筆都是位址基底先就緒，但成為 ROB 隊首後，只有資料未就緒的等待為 0 拍。GEMM 有 7,940 拍，CRC32 有 174,253 拍，隊首 store 正在寫入 SQ，同時外部埠可接受請求。現行設計須等下一拍取得 ROB 授權。

GEMM 的一筆 store（ROB tag 32210）顯示兩個階段如何接續。表中的週期從解除 reset 起算，指該次取樣即將發生的上升緣。

| 事件 | 週期 |
| --- | ---: |
| 位址基底運算元首次被觀察為就緒 | 20,170 |
| store 資料運算元首次被觀察為就緒 | 20,174 |
| AGU 寫入 SQ，store 成為 ROB 頭 | 20,175 |
| ROB 首次授權，可參加資料埠仲裁 | 20,176 |
| 外部資料埠接受寫入 | 20,178 |
| 成功回應與退休 | 20,179 |

## 下一個獨立實驗

建議以 C 為父版本，測試「已在 ROB 隊首、AGU 本拍產生完整位址與資料，而且資料埠空閒時，提前一拍發出 store 請求」。保留現行仲裁優先序與成功回應後才能退休的條件。依目前的排程，可供這個單拍捷徑使用的邊緣，占 Embench 全部週期 **0.585%**、FP32 **0.958%**。個別負載較集中在 gemm（6.44%）、crc32（3.45%）、ud（1.09%）、qrduino（0.91%）、edn（0.89%）。這是觀察到的邊緣占比，程式收益要靠候選 RTL 重跑才能判定。

這個新路徑會把隊首身分、AGU 位址／資料與請求有效訊號接到外部埠。實驗須驗證回壓時請求穩定、單次寫入、flush、未對齊、存取錯誤、精確 trap 與 SQ 狀態一致，並檢查 EX0 到資料埠的實體時序。C 的 1.079442×／1.111306× 仍是已量測的同頻成績。C 的面積及實體時序待測。若要達到兩類均 1.20×，相對 C 的家族幾何平均執行時間仍須分別縮短 10.05% 與 7.39%。[C 的共同時脈結果](../lsu-c-head-v1/README.md) · [ROOM 已量測的 EX0 至 byte-enable 路徑](../../LSU_ROB_ROOM_PHYSICAL.md)

## 證據與重現

觀察器只連結到主機模擬 harness，原始物件重新連結後的控制執行檔與正式 C 執行檔逐位元組相同。27 項均重現原始標準輸出、記憶體稽核及完整 ROI profile。所有 ROI store 的完整 tag、總線寫入內容與實際提交內容均已比對。每項的授權前和確認等待週期都與原有獨立計數對帳。

五組定向控制比對原始 C 模型 VCD 與觀察器。21 筆代表性 store 核對運算元、AGU、隊首、授權、請求、回應與退休或 trap 的實際邊緣。SW 和 FSW 注入存取錯誤時，錯誤回應當拍皆未確認退休，兩拍後進入精確 trap，cause=7、tval 等於錯誤位址。另以 40 ns 回應及週期性回壓核對延遲與阻塞。每份波形都能驗出刻意偏移一拍的請求時間。多加一拍確認等待也會觸發 ROI 對帳失敗。這些定向控制獨立於 27 項的固定記憶體設定。
